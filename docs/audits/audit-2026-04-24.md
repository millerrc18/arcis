## Critical Findings

### [SECURITY] Platform API Routes Completely Unauthenticated

- **Severity**: critical
- **File**: `src/api/cloud_routes/platform.py:74,94,114,131,139,166,222,325` / `src/api/cloud_app.py:285-288`
- **Evidence**: Eight cloud API routes (`/api/platform/strategies`, `/api/platform/backtest-results`, `/api/platform/backtests`, `/api/platform/promotions`, `/api/platform/demotions`, etc.) are registered with `app.include_router(_platform_module.router)` at line 288 — **without** passing `verify_auth`. The module-level comment in `cloud_app.py` says "auth-free in dev" but this app is deployed to Render production. The `verify_auth = None` placeholder in `platform.py:34` is never overwritten; no `_register_platform_router` injection function exists. Any party with the Render URL can promote/demote strategies, trigger backtests, and read all strategy configurations without credentials.
- **Recommendation**: Pass `dependencies=[Depends(verify_auth)]` to each route decorator, or register the router with `app.include_router(_platform_module.router, dependencies=[Depends(verify_auth)])`.

### [SECURITY] Walk-Forward Routes Also Unauthenticated

- **Severity**: critical
- **File**: `src/api/cloud_routes/walkforward.py:60,92,104,136` / `src/api/cloud_app.py:293-294`
- **Evidence**: Four walk-forward routes (`/api/walkforward/runs`, `/api/walkforward/runs/{run_id}`, etc.) are registered at `cloud_app.py:294` the same way — no auth dependency injected. Walk-forward run data contains strategy performance data that should be access-controlled.
- **Recommendation**: Same as above — include `dependencies=[Depends(verify_auth)]`.

### [ARCHITECTURE] Direct sqlite3.connect() in API Route Handlers

- **Severity**: high
- **File**: `src/api/routes/notes.py`, `src/api/routes/logs.py`, `src/api/routes/live.py`, `src/api/routes/council.py`, `src/api/routes/system.py`, `src/api/cloud_routes/platform.py`, `src/api/cloud_routes/walkforward.py`
- **Evidence**: At least 7 API route files call `sqlite3.connect(DB_PATH)` directly in route handler functions, bypassing `src.utils.db.connect_db()` (which applies 30s busy_timeout and row_factory). CLAUDE.md rule: "All Python SQLite connections should use `src.utils.db.connect_db()`". Example: `src/api/routes/notes.py:84` — `conn = sqlite3.connect(DB_PATH)` inside `@router.get("/notes")`.
- **Recommendation**: Replace all `sqlite3.connect(DB_PATH)` callsites in `src/api/` with `connect_db()` from `src.utils.db`. This also fixes potential lock errors under load.

## Medium Findings

### [TRADING SAFETY] IB Paper Trades Skip Post-Submission Order Verification

- **Severity**: medium
- **File**: `src/shadow_trading/executor.py:703`
- **Evidence**: The `open_shadow_trade()` function has two branches — Alpaca (lines 730–767) and IB (lines 703–729). The Alpaca path calls `_verify_and_update()` at lines 745 and 767 to confirm the order was accepted by the broker. The IB path does not call `_verify_and_update()`. Per CLAUDE.md: "Verify orders after submission — call `verify_order_accepted()` after `submit_order()`". Shadow trading is a real-money simulation; unverified orders may appear accepted but be silently rejected by IB.
- **Recommendation**: Add `_verify_and_update()` call (or equivalent IB-aware verification) after IB order submission at line ~722 in executor.py.

### [TRADING SAFETY] 17+ Hardcoded `'closed'` Status Strings Instead of Constants

- **Severity**: medium
- **File**: `src/shadow_trading/executor.py:586,593,2012,2288,2293,2306,2332,2344,2350,2362,2368,2382,2388,2414,2448`, `src/shadow_trading/state.py:30`, `src/scheduler/watch.py:486,494`, `src/scheduler/reports.py:321,335,343`
- **Evidence**: Executor.py alone has 15+ SQL queries using `status='closed'` as a string literal. The module defines `FILLED_ORDER_STATUSES = {"filled", "closed"}` at line 166 but never uses it in SQL. CLAUDE.md: "Status constants are canonical — use `TERMINAL_STATUSES` and `ACTIVE_STATUSES` from `src/shadow_trading/models.py` in queries."
- **Recommendation**: Replace all `status='closed'` literals with constant-driven filtering. For SQL, use a helper that expands the constant set into parameterized `IN (?, ?)` clauses.

### [ARCHITECTURE] Circular Import Workarounds via Late Imports

- **Severity**: medium
- **File**: `src/shadow_trading/executor.py:455+`, `src/platform/promotion.py:50`, `src/api/cloud_routes/platform.py:33`
- **Evidence**: Three modules have explicit comments documenting that imports are deferred inside function bodies to avoid circular import cycles. `executor.py` has 57 function-body imports across the file. This indicates structural coupling problems in the dependency graph.
- **Recommendation**: Introduce a thin `src/interfaces/` module with abstract base types (no concrete imports) to break cycles cleanly.

### [SECURITY] Timing-Attack Vulnerability in API Token Comparison

- **Severity**: medium
- **File**: `src/api/cloud_app.py:145-148`
- **Evidence**: `verify_auth()` compares bearer tokens with `token == _API_SECRET_HASH or token == API_SECRET` — standard string equality, not constant-time comparison. A timing oracle attack is unlikely in practice given HTTPS and network latency, but the fix is trivial.
- **Recommendation**: Replace with `secrets.compare_digest(token, _API_SECRET_HASH) or secrets.compare_digest(token, API_SECRET)`.
