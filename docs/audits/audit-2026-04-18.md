## Critical Findings

### [ARCHITECTURE] API routes directly access SQLite — no service layer

- **Severity**: critical
- **Files**: `src/api/routes/council.py`, `src/api/routes/health.py`, `src/api/routes/system.py`, `src/api/routes/actions.py`, `src/api/routes/ib_status.py`, `src/api/routes/live.py`, `src/api/routes/logs.py`, `src/api/routes/notes.py`, `src/api/routes/scan.py`, `src/api/routes/packets.py`, `src/api/routes/shadow.py`, `src/api/routes/training.py`, and 7 others (19 route files total)
- **Evidence**: 49+ raw `conn.execute()` calls in route handlers. Example `src/api/routes/council.py:52-69`:
  ```python
  conn = sqlite3.connect(DB_PATH)
  conn.row_factory = sqlite3.Row
  session = conn.execute(
      "SELECT * FROM council_sessions ORDER BY created_at DESC LIMIT 1"
  ).fetchone()
  ```
- **Impact**: No repository abstraction — impossible to unit-test routes without a live DB. Migration from SQLite to Postgres would require touching all route files. SQL logic scattered across HTTP layer.
- **Recommendation**: Extract a `src/repository/` or `src/store/` layer. Routes call service functions; service functions call repository functions. Local routes already have `src/journal/store.py` as a model — extend this pattern.

### [TRADING SAFETY] Hardcoded `'closed'` status string in SQL queries — violates CLAUDE.md rule

- **Severity**: critical
- **Files**:
  - `src/risk/governor.py:200` — `WHERE status = 'closed'`
  - `src/scheduler/reports.py:321` — `WHERE status='closed'`
- **Evidence**: CLAUDE.md states: *"use `TERMINAL_STATUSES` and `ACTIVE_STATUSES` from `src/shadow_trading/models.py` in queries. Never hardcode `status != 'closed'`."* These two files bypass that rule.
- **Impact**: If the status lifecycle ever adds a new terminal state (e.g., `'expired'`, `'cancelled'`), these queries silently exclude real closed positions from risk and reporting calculations.
- **Recommendation**: Import and use `TERMINAL_STATUSES` / `ACTIVE_STATUSES` constants from `src/shadow_trading/models.py` in all SQL WHERE clauses touching trade status.

## High Findings

### [ARCHITECTURE] Circular import: `startup.py` ↔ `startup_checks.py`

- **Severity**: high
- **Files**: `src/startup.py:96`, `src/startup_checks.py:20`
- **Evidence**: `startup.py` imports from `startup_checks` at runtime (marked `# noqa: E402` indicating a late/deferred import to break the cycle). `startup_checks.py:20` imports `CheckResult` from `src.startup`. This is a mutual dependency disguised by import ordering.
- **Recommendation**: Extract `CheckResult` (and similar shared types) to a third module `src/startup_types.py` that neither file imports from the other. Both files then import from `startup_types`.

### [CODE QUALITY] Bare `except Exception` swallows context in 13+ API route endpoints

- **Severity**: high
- **Files**: `src/api/routes/system.py` (13 occurrences), `src/api/routes/actions.py` (30 try-except blocks)
- **Evidence**: Pattern throughout route files:
  ```python
  except Exception as exc:
      logger.error(f"...: {exc}")
      return {"error": str(exc)}
  ```
- **Impact**: Swallows stack traces. Different exception types (DB error vs. config error vs. network error) receive identical handling. Makes debugging production failures much harder.
- **Recommendation**: Catch specific exceptions (`sqlite3.OperationalError`, `KeyError`, `ValueError`). Use FastAPI exception handlers for HTTP-layer normalization.

### [COMPLIANCE] `scripts/migrate_production_db.py:75` uses f-string in ALTER TABLE SQL

- **Severity**: medium
- **File**: `scripts/migrate_production_db.py:75`
- **Evidence**: `sql = f"ALTER TABLE {table} ADD COLUMN {column} {col_type}"` — values come from a hardcoded `COLUMN_MIGRATIONS` list (not user input) so injection risk is minimal, but the pattern is fragile if the list ever becomes configurable.
