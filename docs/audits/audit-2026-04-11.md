## Regressions (New Since 2026-04-10)

### [REGRESSION] test_live_trading: 2 tests broken by d974eee (buying power alert feature)

- **Severity**: high
- **Introduced**: commit `d974eee` — `feat(executor): alert on consecutive buying power failures (#358)`, merged 2026-04-10
- **Failing tests**:
  - `tests/test_live_trading.py::TestPaperSourceTagging::test_paper_trade_tagged_as_paper`
  - `tests/test_live_trading.py::TestDualExecution::test_paper_and_live_both_execute`
- **Root cause**: `open_shadow_trade()` now calls `_check_paper_buying_power()` which calls `get_account_info()`. These tests mock `place_bracket_order` and `place_paper_entry` but not `get_account_info`. In the test environment (example config), `get_account_info()` returns `buying_power: $1.00`, causing the pre-check to reject the trade before the bracket order is even attempted. Both tests then fail `assert trade_id is not None`.
- **Fix**: Add `@patch("src.shadow_trading.alpaca_adapter.get_account_info", return_value={"buying_power": 10000.0, "equity": 10000.0, "cash": 10000.0})` to both tests.

### [REGRESSION] test_ingestion_gate: markdown bold heading now accepted when it should be rejected

- **Severity**: high
- **File**: `tests/test_ingestion_gate.py:98`, `src/data_ingestion/gate.py` (or equivalent validator)
- **Failing test**: `tests/test_ingestion_gate.py::test_markdown_bold_heading_rejected`
- **Root cause**: `validate_training_example()` returns `(True, "")` for an input containing `**Market context:**` (markdown bold). The test asserts `ok is False`. Either the markdown-detection regex was weakened/removed in a recent commit, or a new allow-list entry is too permissive.
- **Impact**: Training data quality. Markdown bold formatting in the `context` field of training examples can corrupt the fine-tuning dataset — this was previously caught by the gate.
- **Fix**: Investigate the gate validator's markdown-detection logic and restore the `**...**` pattern rejection.

## Critical Findings

### [ARCHITECTURE] WatchLoop God Object

- **Severity**: critical
- **File**: `src/scheduler/watch.py:102–2004`
- **Evidence**: `WatchLoop` class is 1,903 lines with 60+ methods. The `run()` method alone is 721 lines (lines 1028–1748). The class mixes at least 8 distinct responsibilities: lock management, DB logging, market-open detection, scan orchestration, metrics recording, overnight delegation, daily state management, and signal handling. This is the single point of failure for all automation.
- **Impact**: Untestable in isolation; a bug in any of 60 methods can halt all trading automation. Tight coupling to SQLite (direct calls) makes it hard to mock.
- **Recommendation**: Extract the 30+ `_run_X()` task runners into a `TaskRegistry` / `TaskRunner` abstraction. Split `run()` into `_setup()`, `_configure_infrastructure()`, `_start_background_threads()`, and a slim orchestration loop.

### [TEST COVERAGE] IB Broker Has Zero Test Coverage

- **Severity**: critical
- **File**: `src/trading/ib_broker.py` (13 methods, ~275 lines), `src/trading/broker_factory.py` (2 functions, ~50 lines)
- **Evidence**: No test file targeting `ib_broker.py` found in `tests/`. `broker_factory.py` is untested directly — `test_broker_interface.py` tests the abstract interface but not the IB concrete implementation or the factory singleton logic.
- **Impact**: IB Broker is used for live trades (port 4001/4002). The singleton connection-state management in `broker_factory.get_live_broker()` (lines 26–62) is completely unverified. A regression here could silently use a stale or invalid broker connection for live orders.
- **Recommendation**: Add `tests/test_ib_broker.py` with mocked IB Gateway (mock `src.trading.ib_broker.ib` module). Add `tests/test_broker_factory.py` verifying singleton behaviour and reconnect logic.

### [TEST COVERAGE] Weak Tests — No Real Assertions

- **Severity**: high
- **Files**: `tests/test_bracket_safety.py:60–75`, `tests/test_activity_logger.py:88–93`
- **Evidence**:
  - `test_retry_exit_called_for_exit_failed` (bracket_safety.py:60): Calls `check_and_manage_open_trades()` and asserts only `mock_retry.assert_called_once()` — verifies invocation but not arguments or outcomes.

### [TRADING SAFETY] Bare `except: pass` in Executor — Silences Critical Alerts

- **Severity**: high
- **File**: `src/shadow_trading/executor.py:91–92`, `534–535`, `909`, `944`, `1045`, `1074`
- **Evidence**: Six bare `except Exception: pass` handlers in the executor. While three are in notification-only paths (Telegram alerts for buying-power crisis, unprotected position, and trade attribution), silencing these exceptions means critical operational warnings — "entry filled but stop-loss failed" at line 534 — are swallowed entirely if Telegram is unavailable.
- **Impact**: If Telegram is down and a bracket order partially fills with no stop-loss, the `except: pass` at line 534 means the operator receives **no alert** via any channel. The trade close attempt still runs, but failure of that close is also silenced.
- **Recommendation**: Replace all six `except Exception: pass` with `except Exception as e: logger.warning("[EXECUTOR] notification failed: %s", e)`. This is a one-line change per site and preserves existing behaviour while restoring observability.

## Warnings

### [ARCHITECTURE] Circular Import — Risk Governor ↔ Trade Executor

- **Severity**: medium
- **Files**: `src/risk/governor.py:620`, `src/shadow_trading/executor.py:210,334,356,1370`
- **Evidence**: `governor.py` imports `_get_current_price_safe` from `executor` (lazy, inside function). `executor.py` imports `RiskGovernor`, `drawdown_adjusted_risk`, `get_effective_risk_pct`, `get_portfolio_state` from `governor` (all lazy). All are lazy-loaded so no import error at startup.
- **Recommendation**: Extract the shared pricing helper (`_get_current_price_safe`) and portfolio utilities into a new `src/risk/models.py` or `src/risk/utils.py` to break the cycle cleanly.

### [ARCHITECTURE] Circular Import — Features Engine ↔ Regime

- **Severity**: medium
- **Files**: `src/features/engine.py`, `src/features/regime.py:30`
- **Evidence**: `regime.py` imports `_slope_direction` from `engine.py`. `engine.py` depends on regime computation from `regime.py`. Both are widely imported by training, ranking, and scheduler subsystems.

### [ARCHITECTURE] API Routes Bypass Service Layer — Direct SQLite Access

- **Severity**: medium
- **Files**: `src/api/routes/council.py:23`, `src/api/routes/health.py:24`, `src/api/routes/live.py:20`, `src/api/routes/logs.py:24`, `src/api/routes/notes.py:23`, `src/api/routes/system.py` (multiple)
- **Evidence**: All six route files call `sqlite3.connect(DB_PATH)` directly and run raw SQL queries inline. There is no service/repository layer between the API routes and the database.
- **Impact**: SQL logic is duplicated across route handlers. Schema changes require touching every route file.
- **Recommendation**: Introduce thin service modules (e.g., `src/services/council_service.py`) or a shared `get_db()` dependency. Not a blocking issue for current scale, but a maintenance liability.

### [SECURITY] Local API Has No Authentication

- **Severity**: low (mitigated)
- **Files**: `src/api/app.py`, `src/api/routes/system.py` (and all local routes)
- **Evidence**: Local API routes have no `Depends()`, `HTTPBearer`, or `verify_auth()` guards. The cloud API (`src/api/cloud_app.py`) correctly uses a SHA-256 bearer token check (lines 108–128).
- **Mitigation**: Per CLAUDE.md, local API binds to `127.0.0.1` only. Routes like `/api/halt-trading` and `/api/resume-trading` are accessible to any process on the local machine.
- **Recommendation**: Add optional `X-Local-Secret` header check to high-impact mutation routes (`/halt-trading`, `/resume-trading`, `/api/config`). Low urgency given localhost-only binding.
