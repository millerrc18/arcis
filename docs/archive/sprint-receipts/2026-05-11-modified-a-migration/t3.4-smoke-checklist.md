# T3.4 — 30-Minute Post-Cutover Smoke Checklist

**Date prepared:** 2026-05-11
**Owner:** operator
**Purpose:** Verify the SQLite → Postgres cutover (T3.3 NSSM env flip) is healthy enough to leave running. **Triggers T3.5 rollback** if any **FAIL** criterion below is hit during the window.
**Prerequisite:** T3.0 (env-var baseline audit) + T3.1 (snapshots) + T3.2 PR merged (precedence-flip gate) + T3.3 NSSM env flip executed + both services restarted.

> **Hard-cap timer.** 30 minutes from "ArcisWatchLoop restarted." If you cannot finish all sections in 30 minutes, the cutover is too unstable — invoke T3.5 rollback.

## §1 — Write-path smoke (writes must land in PG, not SQLite) [target: minutes 0-10]

The Phase 2 cutover means every `connect_db()` call in the watch loop now writes to PG. We verify each major write path independently by triggering it + checking PG.

### 1.1 — `system_metrics` snapshot writes (highest-frequency write path)

`src/monitoring/system_metrics.py` writes a row every ~5 min via the watch loop scheduler.

```bash
# Wait 5 min after restart, then query PG:
docker exec halcyon-pg psql -U halcyon -d halcyon -c "SELECT timestamp, gpu_util_pct, cpu_pct, ram_used_mb FROM system_metrics ORDER BY timestamp DESC LIMIT 3;"

# Compare against SQLite to confirm WRITE went to PG, not the legacy file:
sqlite3 -readonly "file:C:/arcis/data/ai_research_desk.sqlite3?mode=ro" "SELECT MAX(timestamp) FROM system_metrics;"
```

**PASS:** PG's `MAX(timestamp)` is newer than SQLite's `MAX(timestamp)` (cutover-time onward). **FAIL:** PG empty or stale → writes still hitting SQLite — `connect_db()` gate didn't flip. → **T3.5 rollback** + investigate why `ARCIS_PG_CUTOVER_ENABLED=1` env var isn't visible to the running Python process (likely an NSSM env-set mistake or service didn't actually restart).

### 1.2 — `shadow_trades` writes (paper trading)

If markets are open: a paper trade entered via `python -m src.main scan` should land in PG. If markets are closed: skip this and rely on §1.3 instead.

```bash
# Trigger a single paper scan with dry-run OFF (creates a real shadow row if any signal qualifies):
python -m src.main scan --verbose
# Or check existing recent insert from prior scan:
docker exec halcyon-pg psql -U halcyon -d halcyon -c "SELECT trade_id, ticker, status, created_at FROM shadow_trades ORDER BY created_at DESC LIMIT 5;"
```

**PASS:** Newest `created_at` in PG `shadow_trades` is post-cutover-timestamp. **FAIL** if newest row is pre-cutover (writes going to SQLite) → **T3.5 rollback.**

### 1.3 — `activity_log` writes (always-on, low-volume)

The watch loop writes activity log entries on every task lifecycle event.

```bash
docker exec halcyon-pg psql -U halcyon -d halcyon -c "SELECT event_type, detail, created_at FROM activity_log ORDER BY created_at DESC LIMIT 10;"
```

**PASS:** At least 1 row with `created_at` post-cutover-timestamp. **FAIL** if PG `activity_log` is empty post-cutover → writes still SQLite → **T3.5 rollback.**

### 1.4 — `notifications_dedup` upserts (heartbeat / telegram dedup)

Every notification fires an `engine_aware_upsert` into `notifications_dedup` (Phase 0 T0.7). Cutover exercises both the SQLite `INSERT OR REPLACE` rewrite AND the PG `ON CONFLICT (event_type, dedup_key) DO UPDATE` path.

```bash
docker exec halcyon-pg psql -U halcyon -d halcyon -c "SELECT event_type, dedup_key, last_fired_at FROM notifications_dedup ORDER BY last_fired_at DESC LIMIT 5;"
```

**PASS:** Recent (post-cutover) `last_fired_at`. **WARN** if no rows yet — wait 10 min, the heartbeat fires periodically; if still empty at minute 20, **FAIL** (notification pipeline crashed silently against PG).

### 1.5 — `scan_metrics` writes (per scan-cycle)

```bash
docker exec halcyon-pg psql -U halcyon -d halcyon -c "SELECT scan_time, decisions_made, llm_total FROM scan_metrics ORDER BY scan_time DESC LIMIT 3;"
```

**PASS:** Newest row post-cutover. **FAIL** if empty/stale (write path broken) → **T3.5 rollback.**

## §3 — C1 regression coverage: activity_log LIKE path [target: minutes 15-20]

**Why this section exists.** The Phase 0 wrapper's `_rewrite_question_to_pct` has a quote-and-percent-aware path: it rewrites `?` → `%s` while leaving the operator's `%` wildcards in LIKE patterns untouched, AND escapes unpaired `%` outside literals to `%%` so psycopg2's parameter binding doesn't crash. C1 was the regression-class where this rewrite previously corrupted LIKE patterns (an `f"%{threshold}%"` parameter bound through the wrapper would either lose its `%` or double them).

### 3.1 — `executor.py:777` drawdown-alert LIKE site

This site fires only when a drawdown threshold is crossed AND `current_dd_pct >= threshold` (5/10/15%). In a passing portfolio, may not fire naturally during the 30-min window.

**Synthetic trigger (operator option, only if §3.2 doesn't already pass):**

```python
# In a Python REPL with .env loaded (will route through cutover-enabled connect_db):
from src.utils.activity_logger import log_activity
log_activity("smoke_test_like", "smoke 5%")
log_activity("smoke_test_like", "smoke 10%")
# Then query through the same wrapper-routed path:
from src.utils.db import connect_db
with connect_db() as conn:
    rows = conn.execute(
        "SELECT detail FROM activity_log WHERE event_type = ? AND detail LIKE ?",
        ("smoke_test_like", "%5%")
    ).fetchall()
    print(rows)
```

**PASS:** Returns ≥1 row containing `smoke 5%`. **FAIL:** psycopg2 raises `IndexError` / `ValueError` / `OperationalError` on parameter binding → the C1 rewrite is broken → **T3.5 rollback** + file as P0 bug.

### 3.2 — `reports.py` LIKE prefix sites (~14 sites, fire daily/hourly)

The reports module uses `WHERE created_at LIKE 'YYYY-MM-%'` patterns for monthly rollups. These should fire naturally as the watch loop progresses through its cadence. Check the dashboard's "Daily Report" tile (if visible) or:

```bash
# Inspect the per-week report path:
curl -s "https://halcyonlab.app/api/reports/weekly" -H "Authorization: Bearer $API_SECRET" | jq '.' | head -50
```

**PASS:** Returns JSON with non-empty fields. **FAIL:** 500 → LIKE path broken → **T3.5 rollback.**

### 3.3 — `shadow_trading/executor.py:2521` `created_at LIKE ?` against `shadow_trades`

Fires inside the per-cycle position-reconciliation loop. Naturally exercises during any market-hours cycle.

```bash
docker exec halcyon-pg psql -U halcyon -d halcyon -c "EXPLAIN ANALYZE SELECT trade_id FROM shadow_trades WHERE source='live' AND created_at LIKE '2026-05-%' LIMIT 5;"
```

**PASS:** Query plan returns rows or 0 rows cleanly. **FAIL:** psycopg2 error → C1 wrapper bug → **T3.5 rollback.**

## §4 — Log sweep (no critical errors in the smoke window) [target: minutes 20-25]

Inspect both service logs for the 30-min window. The error patterns below are **cutover-specific**; pre-existing chronic warnings are tolerated.

```bash
# Watch-loop log (last 30 min of entries):
Get-Content C:\arcis\logs\watch.log -Tail 500 | Select-String -Pattern "OperationalError|KeyError|psycopg2|relation .* does not exist|column .* does not exist|syntax error at or near|sqlite3.OperationalError"

# Dashboard log:
Get-Content C:\arcis\logs\dashboard.log -Tail 500 | Select-String -Pattern "OperationalError|KeyError|psycopg2|relation .* does not exist|column .* does not exist|syntax error at or near"
```

### Decision matrix per pattern

| Pattern | Severity | Action |
|---------|----------|--------|
| `relation "X" does not exist` | **CRITICAL** | Table missing in PG. § 0.6 re-mirror failed or table is new since cutover. → **T3.5 rollback.** |
| `column "X" does not exist` | **CRITICAL** | Schema drift between SQLite + PG. → **T3.5 rollback.** File as schema-drift incident. |
| `syntax error at or near "?"` | **CRITICAL** | A `?` placeholder reached PG un-rewritten (Phase 0 wrapper bug). → **T3.5 rollback** + file as P0. |
| `syntax error at or near "PRAGMA"` | **CRITICAL** | A PRAGMA site was missed in Phase 2 KNOWN_OFFENDERS migration. → **T3.5 rollback** + file as P0. |
| `KeyError: 0` from psycopg2 RealDictRow | **HIGH** | The T2.6 row[0][0] tuple-indexing class. Filed as follow-up; cosmetic if it doesn't crash the watch loop. If it crashes the loop → **T3.5 rollback.** Otherwise note and continue. |
| `psycopg2.OperationalError: connection ... lost` | **MEDIUM** | Transient PG-disconnect. The M3 fast-exit + NSSM restart should handle. If NSSM restart fires successfully → continue smoke. If restart loops more than 3× in 5 min → **T3.5 rollback.** |
| `database is locked` | **CRITICAL (unexpected)** | This is a SQLite-only error. If it appears post-cutover, a code path is STILL writing to SQLite. → file as P0; doesn't necessarily rollback unless writes are missed. |
| `sqlite3.OperationalError: no such table` | **WARN** | Some explicit-`db_path` call site is reading from SQLite (the legacy explicit path). Tolerable if cutover-isolated; investigate post-smoke. |

## §5 — Decision (minute 30)

### PASS criteria (all of)
- §0 pre-smoke gates: 7/7
- §1 write paths: all 5 confirmed writing to PG (or §1.2 deferred due to closed market)
- §2 read paths: ≥6/7 endpoints clean (single cosmetic 500 tolerated)
- §3 C1 regression: §3.1 or §3.2 confirmed PASS (one is sufficient if both pathways exercise the rewrite); §3.3 not 500
- §4 log sweep: zero CRITICAL patterns

→ **Continue with cutover.** Cutover is committed. Monitor watch.log for next 24h; file any new error classes as P1.

### DEGRADED (cutover stays up, but file P1 follow-ups)
- All write paths PASS but ≥1 cosmetic 500 on read endpoints
- §3 PASS but `KeyError: 0` appears in logs (T2.6 class)
- Single non-blocking warning in §4

→ **Continue with cutover.** File P1 follow-up tickets. **Do not** trigger T3.5 just for warnings.

### FAIL → T3.5 ROLLBACK
- Any §0 gate fails after a retry
- Any §1 write-path verifies as still hitting SQLite
- ≥3/7 §2 endpoints return 500, or `/api/kpis` is fully empty
- §3 C1 site raises psycopg2 binding error
- Any §4 CRITICAL pattern appears (relation/column missing, syntax error at `?` or PRAGMA, NSSM restart-loop)

**T3.5 rollback procedure:**

```bash
# Single env var unset reverts cutover to SQLite:
nssm set ArcisWatchLoop AppEnvironmentExtra @existing-env-without-cutover-flag
nssm set ArcisDashboard AppEnvironmentExtra @existing-env-without-cutover-flag

# Or, simpler — just remove the flag while keeping DATABASE_URL (which becomes inert without the gate):
# Open NSSM GUI → ArcisWatchLoop → Environment tab → delete ARCIS_PG_CUTOVER_ENABLED=1 line → OK
# Then:
nssm restart ArcisWatchLoop
nssm restart ArcisDashboard

# Verify revert:
Get-Content C:\arcis\logs\watch.log -Tail 20  # should resume SQLite-backed activity within ~30s
```

After rollback: file a P0 incident report with the §4 log excerpt + which §1 / §2 / §3 step failed + which CRITICAL pattern fired. The spec's §6.3 rollback decision tree (in `spec.md`) covers the four major failure modes.

## Appendix B — Quick reference: T3.5 rollback signals

If you see any of these, stop the smoke and roll back immediately:

- `data/watchdog.txt` populated with `PG_CONNECT_FAIL:` → M3 fast-exit fired (PG unreachable)
- NSSM service event log shows ≥3 restarts within 5 min → restart loop (zombie watchdog mitigation)
- `nssm get ArcisWatchLoop AppEnvironmentExtra` is missing `PYTHONUTF8` or `ARCIS_DB_PATH` → T3.3 env update overwrote instead of appended (training pipeline broken)
- Any `relation "X" does not exist` or `column "X" does not exist` in watch.log → schema drift (re-run `render_migrate.py` before retrying cutover)
