## Critical Findings

### [ARCHITECTURE] Confirmed Circular Import: startup.py ↔ startup_checks.py

- **Severity**: critical
- **Files**: `src/startup.py:96`, `src/startup_checks.py:20`
- **Evidence**:
  ```
  src/startup.py:96     → from src.startup_checks import (check_config, ...)
  src/startup_checks.py:20 → from src.startup import CheckResult
  ```
  Importing `startup_checks` directly triggers a live `ImportError`:
  ```
  ImportError: cannot import name 'check_config' from partially initialized module
  'src.startup_checks' (most likely due to a circular import)
  ```
  Only works when `startup.py` is the entry point because Python's module cache partially
  initializes `startup` before reaching line 96. Any code path that imports
  `startup_checks` first (e.g. tests, tooling) will fail at runtime.
- **Recommendation**: Move `CheckResult` to a standalone `src/models/startup_result.py`
  (no imports from `src.startup` or `src.startup_checks`). Both modules import from there.

### [TEST COVERAGE] Failing Test: `test_coerce_to_schema::test_integer_column_coercion`

- **Severity**: critical
- **File**: `tests/test_coerce_to_schema.py:67-70`
- **Evidence**:
  ```python
  # Test assumes planned_shares is INTEGER:
  result = _coerce_to_schema("shadow_trades", {"planned_shares": "100"})
  ```

  In `src/schema/registry.py:188`, `planned_shares` is declared `REAL` (not `INTEGER`)
  to support Alpaca fractional shares. The coercion function correctly returns `float(100) =
  100.0`. The test was not updated when the column type was changed.
  ```
  FAILED tests/test_coerce_to_schema.py::TestCoerceToSchema::test_integer_column_coercion
  AssertionError: isinstance(100.0, int) is False
  ```
- **Recommendation**: Update the test to use an actual INTEGER column (e.g.
  `duration_days` or `earnings_adjacent`) and add a separate assertion that confirms
  `planned_shares` is now coerced to float as intended by the schema.

### [TRADING SAFETY] ImportError in Bracket Fallback Silently Leaves Position Unprotected

- **Severity**: critical
- **File**: `src/shadow_trading/executor.py:724-725`
- **Evidence**:
  ```python
  except ImportError:
      logger.warning("[SHADOW] Stop order imports unavailable for %s — position unprotected", ticker)
  ```
  The outer `try` block at line 687 covers the entire stop-loss + emergency-close
  logic. If `alpaca.trading.requests` or `alpaca.trading.enums` cannot be imported, the
  `ImportError` is caught at line 724 — and no stop-loss is submitted, no emergency close
  is attempted, and no Telegram alert is sent. The position is entered with unlimited
  downside and no audit trail. The entry fills successfully (line 626-660), but the
  protective layer is silently skipped.
- **Recommendation**: Move `from alpaca.trading.requests import ...` and
  `from alpaca.trading.enums import ...` to the module top-level (line ~45). An import
  failure should surface at startup, not silently suppress stop-loss protection at trade
  time. The `except ImportError` catch block at line 724 should be removed entirely.

### [CODE QUALITY] 56 Broad `except Exception` Handlers in executor.py

- **Severity**: high
- **File**: `src/shadow_trading/executor.py`
- **Evidence**: `except Exception` appears 56 times — it catches code bugs, API errors, DB
  errors, and network errors identically, making post-incident analysis very difficult.
  Line 1239–1240 silently swallows bracket status check failures and falls back to price
  polling with only a WARNING log.
- **Recommendation**: Narrow handlers to specific types: `alpaca.common.exceptions.APIError`,
  `ConnectionError`, `TimeoutError`, `sqlite3.Error`. Reserve `except Exception` for
  genuine top-level safety nets.

### [COMPLIANCE] 25+ Hardcoded Status Strings Violate CLAUDE.md Rule

- **Severity**: high
- **Files**: `src/shadow_trading/executor.py`, `src/shadow_trading/reconcile.py`,
  `src/shadow_trading/bracket_monitor.py`
- **Evidence**: CLAUDE.md line 123 mandates use of `TERMINAL_STATUSES` and `ACTIVE_STATUSES`
  from `src/shadow_trading/models.py`. Neither constant is imported in `executor.py`.
  Instead, status strings are hardcoded in SQL and conditionals:
  ```python
  # executor.py:56
  "WHERE status IN ('open', 'exit_pending')"
  # executor.py:446
  "SELECT trade_id FROM shadow_trades WHERE ticker = ? AND status = 'open'"
  # reconcile.py:573
  "WHERE source = 'paper' AND status IN ('exit_failed', 'exit_pending')"
  ```
  18 instances in `executor.py`, 4 in `reconcile.py`, 2 in `bracket_monitor.py`.
  If a new status is added to `ACTIVE_STATUSES`, queries will silently miss it.
- **Recommendation**: Import `ACTIVE_STATUSES`/`TERMINAL_STATUSES` in each module. Build
  a helper: `_in_clause(statuses)` that generates the `IN (?, ?, ?)` SQL fragment.

### [TRADING SAFETY] Zero Equity Edge Case Allows Any Position Size

- **Severity**: high
- **File**: `src/risk/governor.py:478-483`
- **Evidence**:
  ```python
  if equity > 0:
      position_pct = allocation_dollars / equity
      size_ok = position_pct <= self.max_position_pct
  else:
      position_pct = 0
      size_ok = True   # ← ALLOWS POSITION when equity is 0
  ```
  On a new account or after data corruption, `equity = 0` causes any allocation to pass
  the position-size gate unconditionally.
- **Recommendation**: Treat `equity <= 0` as a data error: `size_ok = False` with a
  CRITICAL log. Never allow a trade when equity cannot be determined.

### [TRADING SAFETY] Risk Governor Parameters Not Bounds-Checked

- **Severity**: medium
- **File**: `src/risk/governor.py:350-366`
- **Evidence**: `RiskGovernor.__init__` reads `max_daily_loss_pct`, `max_position_pct`,
  and `vol_halt_pct` directly from config with no validation. A misconfiguration like
  `max_daily_loss_pct: 0.99` silently allows 99% daily drawdown before halting.
- **Recommendation**: Add assertions: `assert 0 < max_daily_loss_pct <= 0.10`,
  `assert 0 < max_position_pct <= 0.25`, `assert vol_halt_pct > 10`. Raise
  `CollectorConfigError` on violation.

### [SECURITY] SQL f-strings Using Table/Column Names from Internal Whitelist

- **Severity**: medium (architecture-mitigated, defense-in-depth gap)
- **Files**: `src/sync/render_sync.py:146,150,171,177,197`, `src/api/cloud_routes/core.py:311`,
  `src/api/routes/logs.py:73`
- **Evidence**: Multiple queries use `f"SELECT * FROM {table_name}"` pattern. Currently
  safe because `table_name` comes exclusively from the schema registry (hardcoded
  `TableDef` objects). However, there is no identifier escaping, so a future refactor
  that passes user-supplied table names would introduce SQL injection.
- **Recommendation**: Wrap table/column interpolations in a validation helper:
  `_safe_ident(name)` that asserts membership in `TABLES`. Adds one line of protection
  with no performance cost.

### [SECURITY] Cloud Authentication Uses Timing-Sensitive Comparison Fallback

- **Severity**: low
- **File**: `src/api/cloud_app.py:127-128`
- **Evidence**:
  ```python
  token == _API_SECRET_HASH or token == API_SECRET
  ```
  The SHA-256 hash comparison is constant-time via `hmac.compare_digest` (line 127), but
  the fallback `token == API_SECRET` uses Python's built-in string equality, which may be
  timing-sensitive on CPython. In practice, the hashed path executes first and the
  plaintext fallback is rarely reached, so real-world risk is minimal.
- **Recommendation**: Wrap both comparisons in `hmac.compare_digest`.
