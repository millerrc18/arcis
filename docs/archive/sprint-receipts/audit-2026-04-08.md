## Critical Findings

### [TRADING SAFETY] Fractional Share Truncation in BrokerPosition Causes Reconciliation Failure

- **Severity**: critical
- **File**: `src/trading/alpaca_broker.py:155`, `src/trading/broker_interface.py:60`
- **Evidence**:
  - `BrokerPosition.quantity` is typed `int`
  - `AlpacaLiveBroker.get_all_positions()` converts all positions via `int(float(pos.get("qty", 0)))` at line 155
  - `int(float(0.30)) == 0` — fractional share positions (qty < 1.0) are silently truncated to zero
  - The reconciliation guard at `reconcile.py:63` rejects `qty <= 0` as "short positions"
  - This causes **real fractional-share positions to be permanently orphaned** — they will never reconcile and the system cannot close them automatically
  - **Confirmed by two failing test cases**: `test_reconcile_backfills_orphaned` and `test_reconcile_ignores_paper_trades` both fail with `qty=0.0` in the warning log when the mock fixture has `qty=0.30`
- **Impact**: Any live fractional share position entered via paper/live trading will silently fail reconciliation. If the broker holds 0.30 shares of AAPL, the reconciler sees qty=0 and rejects the backfill, leaving the position untracked. This breaks the stop-loss monitoring and post-close accounting for all fractional positions.
- **Recommendation**:
  1. Change `BrokerPosition.quantity` and `BrokerOrder.quantity` types from `int` to `float` in `broker_interface.py`
  2. Remove all `int()` wrapping of qty values in `alpaca_broker.py` — use `float()` directly
  3. Update the reconcile guard to `qty < 0` (only reject truly negative values — fractional longs are valid)
  4. Fix the test fixture: `MOCK_ALPACA_POSITIONS` qty=0.30 should survive the full pipeline

### [TRADING SAFETY] Missing stop_price > 0 Guard Before Bracket Order Placement

- **Severity**: critical
- **File**: `src/shadow_trading/executor.py:263,388`
- **Evidence**:
  - `stop_price = _parse_price(packet.stop_invalidation)` at line 263 returns `0.0` if the LLM output is unparseable
  - `_parse_price` documents: "Returns 0.0 on unparseable input" (`executor.py:94`)
  - `place_bracket_order(..., stop_loss_price=stop_price)` at line 388 is called with no `stop_price > 0` guard
  - The only price check between lines 263–388 is `if entry_price > 0` for share count (line 342) — stop_price is never validated
  - The live trading path (`executor.py:1403,1461`) also passes stop_price to `broker.place_bracket_order` without a `> 0` guard
  - The paper path fallback (standalone stop order) at line 444 correctly checks `stop_price > 0` — but the primary bracket path does not
- **Impact**: If the LLM returns a malformed `stop_invalidation` field, a bracket order is submitted to Alpaca with `stop_price=0`. Alpaca will reject the order (price validation), causing the bracket to fail. The code then falls back to a simple market order without a stop-loss, leaving the position unprotected. A malformed LLM packet can bypass the mechanical stop entirely.
- **Recommendation**: Add a guard immediately after `stop_price = _parse_price(packet.stop_invalidation)` in both the paper path (line 263) and live path (line 1403):
  ```python
  if stop_price <= 0:
      logger.error("[SHADOW] stop_price=0 for %s — rejecting trade (LLM parse failure)", ticker)
      return None
  ```

### [COMPLIANCE] DDL Outside Schema Registry Not Fully Remediated

- **Severity**: high
- **Files**:
  - `scripts/recover_from_postgres.py:148` — `CREATE TABLE IF NOT EXISTS {table} ({col_defs})` with all-TEXT schema (persists from prior audit)
  - `scripts/migrate_production_db.py:75` — `ALTER TABLE {table} ADD COLUMN {column} {col_type}` (COLUMN_MIGRATIONS hardcoded list, not from registry)
- **Evidence**:
  ```
  grep -rn "CREATE TABLE" scripts/ --include="*.py"
  scripts/recover_from_postgres.py:148: sq.execute(f"CREATE TABLE IF NOT EXISTS {table} ({col_defs})")
  
  grep -rn "ALTER TABLE" scripts/ --include="*.py"
  scripts/migrate_production_db.py:75: sql = f"ALTER TABLE {table} ADD COLUMN {column} {col_type}"
  ```
  - `scripts/fetch_earnings_calendar.py` was correctly fixed since the 2026-04-04 audit (no DDL found) — partial remediation
  - `migrate_production_db.py` `migrate_tables()` now delegates to the schema registry (good), but `migrate_columns()` at line 54–75 has a hardcoded `COLUMN_MIGRATIONS` list that issues `ALTER TABLE` outside the registry
  - The CI guardrail `test_no_create_table_in_source` and `test_no_alter_table_in_source` only scan `src/` not `scripts/` — these violations are invisible to CI
- **Impact**: `recover_from_postgres.py` creates tables with all-TEXT columns, overriding the type-annotated schema from the registry. If run during a disaster recovery, schema types will be wrong system-wide. `migrate_production_db.py` COLUMN_MIGRATIONS adds columns that may diverge from the registry.
- **Recommendation**:
  1. `recover_from_postgres.py`: Replace the dynamic `CREATE TABLE` with `initialize_database(sq_path)` so recovery uses the registry schema
  2. `migrate_production_db.py`: Remove `COLUMN_MIGRATIONS` list — supersede it entirely with `python -m src.main validate-schema --fix`
  3. Extend CI guardrails to scan `scripts/` as well as `src/`

### [ARCHITECTURE] God File: watch.py (3,393 lines, 62 methods)
- **Severity**: medium
- **File**: `src/scheduler/watch.py`
- **Evidence**: Largest file in codebase at 3,393 lines with 62 `def` entries including `WatchLoop` class with 40+ methods spanning data collection, trading, training, reconciliation, notifications, and DB management
- **Recommendation**: Extract cohesive subsets (e.g., overnight tasks, data collection scheduling) into dedicated scheduler modules. This would reduce the blast radius of changes and improve testability.

### [ARCHITECTURE] Local API Exposes Sensitive Endpoints Without Authentication
- **Severity**: medium
- **File**: `src/api/routes/system.py:156,169`, `src/cli/commands.py:1176`
- **Evidence**:
  - `POST /halt-trading` and `POST /resume-trading` at `system.py:156,169` have **no authentication** on the local API
  - `PUT /config` at `system.py:359` modifies the YAML config file with no auth
  - The local app binds to `host="0.0.0.0"` at `commands.py:1176`
  - CORS is correctly restricted to `localhost:5173` and `localhost:3000` — but any process on the host can call these endpoints
- **Recommendation**: The local API is intended for the local dashboard only. Consider adding a local secret token (e.g., a file-based token checked on write endpoints) or at minimum bind to `127.0.0.1` instead of `0.0.0.0` to prevent remote access in shared/cloud environments.

### [SECURITY] SQL f-string Queries with Table/Column Names from Hardcoded Sources
- **Severity**: low (informational)
- **File**: Multiple files including `src/evaluation/system_validator.py:184,229`, `src/features/traffic_light.py:41–215`, `src/api/routes/logs.py:73`
- **Evidence**: Multiple locations use f-strings to embed table/column names in SQL. All reviewed cases construct the variable parts from **hardcoded internal tuples/lists** (not user input), and use parameterized `?`/`%s` placeholders for all user-controlled values.
- **Impact**: No immediate injection risk — table names come from `TABLES_SHOULD_HAVE_DATA`, hardcoded `for table, time_col in [...]` lists, etc. However, static analysis tools will flag these, and a future refactor that accidentally wires in user input would create a real vulnerability.
- **Recommendation**: Document the safety justification at each f-string SQL site, and consider using a validated table-name whitelist helper if the pattern grows.
