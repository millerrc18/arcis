## Edge case investigation — empty-dict cases (34% of smoke sample)

Diagnosed three representative empty-dict cases from the smoke sample. Pattern is consistent: **the upstream fetcher (`_fetch_filing_text` → `_lookup_primary_document`) pulled a non-narrative document** instead of the actual 10-K/10-Q/8-K HTML.

| accession | form | text starts with | diagnosis |
|---|---|---|---|
| `000035495025000217` | 10-Q | `hd-20250803 0000354950 2/1 2025 Q2 false xbrli:shares iso4217:USD...` | iXBRL financial fact blob, no narrative |
| `0001564590-19-025065` | 10-K | `SEC EDGAR Submission 0001564590-19-025065 0001564590-19-025065.hdr.sgml :...` | SGML header / metadata file, no narrative |
| `000003610424000037` | 10-Q | `usb-20240331 US BANCORP \DE\ false 2024 Q1 0000036104 12/31...` | iXBRL with `us-gaap:*` namespaced facts |

The parser correctly returns `{}` for these — there are no `Item N. …` narrative sections to match. **This is not a parser bug.** It is an upstream data-quality issue: for some filings, the "primary document" resolved by `_lookup_primary_document` is the structured XBRL extract or SGML header rather than the HTML narrative.

Out of scope for v0.25.5. Recommend filing a follow-up issue for v0.25.6+: "Fetcher returns XBRL/SGML instead of narrative HTML for ~34% of filings." That work belongs in `src/data_collection/edgar_historical.py::_lookup_primary_document`, not the parser.

## Empty-dict storage semantics — decision needed

The collector at `edgar_collector.py:351` writes `NULL` when `_parse_sections` returns `{}`:

```python
json.dumps(sections) if sections else None,
```

For the backfill script, this creates a choice:

**Option 1 (collector-parity):** Write `NULL` when parser returns `{}`.
- Pro: byte-identical semantics to the existing 1,518 rows (0 have `sections_json = '{}'`).
- Con: re-running the backfill re-parses the same ~1,273 empty-dict rows every time. Not idempotent in practice.

**Option 2 (mark-attempted):** Write `'{}'` (literal JSON empty object) when parser returns `{}`.
- Pro: idempotent — row is marked "attempted, no narrative found"; next run's `WHERE sections_json IS NULL` skips it.
- Pro: downstream consumers can distinguish "never parsed" from "parsed, nothing there."
- Con: diverges one-way from the collector's inline semantics. 1,273 new rows with `'{}'` would be visible in queries that existing code doesn't expect.

**Recommendation: Option 2**, because:

1. This sprint is explicitly a one-shot idempotent backfill; re-running should be a no-op, not a re-parse.
2. The upstream fetcher issue diagnosed above means the 34% empty-dict is a persistent data-quality signal, not transient. Tracking it in-schema (via `'{}'` vs `NULL`) is exactly the kind of signal a future operator will want to query.
3. No existing code path (that I could find via grep for `sections_json`) relies on `sections_json IS NULL` semantics that would break on `'{}'`. Consumers parse the JSON directly.

**Operator confirmation required before Pass 3 execution.**
