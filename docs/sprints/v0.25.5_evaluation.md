## Symptom recap — why coverage is 28%

The collector at `src/data_collection/edgar_collector.py:329-331` parses sections inline when full text is available:

```
full_text = _fetch_filing_text(cik, accession)
...
sections = _parse_sections(full_text, form) if full_text else {}
```

For rows collected BEFORE the fetch path was fixed (issue tracked in `docs/research/2026-04-16-research-desk-sprint-review.md:36`), `full_text` was `NULL` at insert time, so `sections_json` went in as `NULL` too. The fulltext backfill on 2026-04-19 restored `full_text` for those rows — but it did **not** re-run `_parse_sections`. This sprint closes that loop.

## Parser entry point

**Location:** `src/data_collection/edgar_collector.py:183`

**Signature:** `_parse_sections(text: str, form_type: str) -> dict[str, str]`

**Properties** (verified by inspection + benchmark):

- Pure function — no I/O, no DB, no network. Regex only.
- Returns `{}` on empty/missing text or no regex matches (defensive — no exception thrown on bad input).
- Truncates each extracted section to 50,000 chars.
- Supports `10-K`, `10-K/A`, `10-Q`, `10-Q/A`, `8-K`. Other form types fall through the 8-K branch (`all_items`).
- **No exceptions expected in normal operation.** Wrapping the call site in `try/except Exception` is a guard for regex catastrophic-backtracking on pathological input only.

**Decision B (operator):** promote to public `parse_sections`. Rename is 1 line at definition site; three callsites + six test references update accordingly. Net diff ≈ 11 lines.

## Transaction model

Per CLAUDE.md: use `src.utils.db.connect_db()`. `busy_timeout=30s`, row factory `sqlite3.Row`.

**Commit cadence (Decision D):** batch every **100 rows**. At 3,743 rows → 38 batch commits. Each batch releases locks cleanly, minimizing contention with any concurrent reader. Per-row commits would be 3,743 tiny transactions — unnecessary given the parser's determinism and the fsync overhead.

**Crash-safety:** each batch-commit is atomic. If the script dies mid-batch (≤100 rows worth of progress lost, re-runnable on next invocation because the query filters `sections_json IS NULL`).

## Error handling strategy (Decision C)

**No schema change.** Failures write to `docs/sprints/v0.25.5_parse_failures.log` (append-only text file, one record per failed row). Format:

```
<ISO8601 timestamp>	<accession_number>	<form_type>	<full_text_length>	<exception_class>	<exception_message_first_200_chars>
```

Expected failure modes:

- Regex catastrophic backtracking on malformed text → `re.error` or timeout (parser has no timeout; mitigated by the 50k-char per-section truncation the parser already does AFTER matching).
- Non-English or encoding-artifact text → parser returns `{}` which is **not a failure** (valid empty result; row gets `sections_json = '{}'`).
- Sqlite `database is locked` while the watch loop is running → should not happen (operator will stop the loop; `busy_timeout=30s` handles incidental cases).

**Per-row exception policy:** catch `Exception`, log, continue. One bad row never halts the run. Failed rows remain `sections_json = NULL` and are retry-eligible on next invocation.
