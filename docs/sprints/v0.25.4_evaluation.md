## Part A — VIX enrichment

### Symptom recap

`docs/validation/lazy-prices-v1-walkforward-real-2026-04-19.md` (v0.25.3 validation):

> `vix_at_entry` and `vix_tier` are **NULL for 20 / 20 OOS trades**. This drives `vix_tier_coverage = 0` at the run level.

Same gap reproduced in v0.26.2-scoped (3/3 trades). Filed as v0.25.4 follow-up by the operator.

### Root-cause analysis

The runner persists `vix_at_entry` straight from the trade object:

```
src/platform/rigor/walkforward_runner.py:354-374
  ... vix_at_entry, vix_tier, ...
       getattr(t, "vix_at_entry", None) or (t.get("vix_at_entry") if isinstance(t, dict) else None),
       _assign_vix_tier(t),
```

`_assign_vix_tier()` itself reads back `getattr(trade, "vix_at_entry", None)` and tier-buckets it via `vix_tier_of()` from `walkforward_metrics.py:147-159` (low <15, medium 15-25, high >25). Tier bucketing is correct — the gap is purely upstream.

The trade object is a `BacktestTrade` dataclass produced by the backtest engine:

```
src/platform/backtest_engine.py:60-77
@dataclass
class BacktestTrade:
    trade_id: str
    ticker: str
    entry_date: str
    exit_date: str
    entry_price: float
    exit_price: float
    shares: int
    pnl_dollars: float
    pnl_pct: float
    exit_reason: str
    hold_days: int
    spy_return_over_hold: float | None
    excess_return: float | None
    realized_sector: str | None
    regime_at_entry: str | None
    metadata: dict = field(default_factory=dict)
```

**No `vix_at_entry` field exists.** So `getattr(t, "vix_at_entry", None)` always returns None, then `vix_tier_of(None)` returns None, then NULL is persisted. Reproduced 23/23 trades across v0.25.3 + v0.26.2-scoped.

|---|---|---|---|---|---|

| FRED `VIXCLS` | yes (1990+) | no | manual | new mock surface | API key (`FRED_API_KEY`) |

yfinance is the only source that meets all four critical constraints (full 2019-2024 coverage + already wired + zero-config auth + reuses existing test mock surface). The cache is symbol-agnostic (`safe_ticker = ticker.replace(".", "_").replace("/", "_")` — `^VIX` becomes `_VIX_<start>_<end>.parquet`).

`to_yfinance_ticker` in `src/universe/sp100.py` may transform the symbol — Pass 2 will verify it passes `^VIX` through unchanged (it operates on dot-suffixed ADRs like `BRK.B`, not caret-prefixed indices).

### Decision A2 — Enrichment injection point: `_build_trade()`

**Chosen.** `src/platform/backtest_engine.py:219-264`. Single function constructs every `BacktestTrade` — both the `_run_scheduled` and `_run_event_driven` paths flow through it (lines 290-294 and 349-353 respectively). Wiring VIX once here covers both entry kinds.

Concrete plan (Pass 3 implementation, sketched here for completeness):

1. Add `vix_at_entry: float | None = None` to `BacktestTrade` dataclass (field 16, after `regime_at_entry`).
2. Add a small helper `_lookup_vix_at_entry(entry_iso: str) -> float | None` near `_attribute_vs_spy` — same pattern: thin wrapper around `fetch_cached_ohlcv("^VIX", entry_iso, +N_days)` that returns the Close on `entry_iso` or the most-recent prior trading day if `entry_iso` itself is non-trading.
3. Call the helper inside `_build_trade()` after `entry_iso` is settled but before the `BacktestTrade(...)` constructor — pass through to the new field.
4. The runner picks it up automatically (no runner change needed) — verified by reading `walkforward_runner.py:354-374`.

**Anti-injection-points considered + rejected:**

- `walkforward_runner.persist_run_result()`: would require re-querying VIX per trade in the persist layer, splitting the data-construction boundary. Worse, it would be invoked once per trade write, not once per ticker per day, multiplying cache lookups.
- `walkforward_runner.run_walkforward()` post-process: same problem; framework code shouldn't touch market data lookups.
- `scripts/backtest/run_walkforward.py` CLI: would re-introduce the upstream/downstream bug surface (CLI does enrichment, but other callers of the engine don't).

### Decision A3 — Cache strategy: per-(start,end) parquet, same as stock OHLCV

**Chosen.** Reuses `fetch_cached_ohlcv` semantics. First call materializes `_VIX_<start>_<end>.parquet`; subsequent calls hit the cache. For walk-forward with N tickers across an OOS window, the engine already calls `load_ohlcv_range(ticker, start, end)` once per ticker — one additional `^VIX` call per ticker per window is acceptable overhead (and the cache makes repeated runs ~free).

Pass 2 will quantify the overhead by counting ticker × window calls in the v0.25.3 reproduction.

### Anti-goals (Part A)

- **No backfill of historical walk-forward runs.** The 20 v0.25.3 trades and 3 v0.26.2-scoped trades stay NULL. Backfill is a follow-up issue if operator wants.
- **No new VIX collector.** `vix_collector.py` continues to write current snapshots only; we don't add historical mode.
- **No changes to R6 `min_vix_tiers` gate.** Once `vix_at_entry` populates, `distinct_tier_count` works without modification — verified by reading `walkforward_metrics.py:215-220` and `walkforward_runner.py:254`.

## Part B — Window-duration surfacing

### Symptom recap

v0.25.3's Window 4 is 274 days (2024-01-01 → 2024-09-30) vs the 4 standard 15-month windows (~456 days each). The 9-month window contributed only 1 OOS trade and produced INCONCLUSIVE_DATA — but the operator can't distinguish that from "strategy didn't signal" because both paint the same state.

### Option 1 vs Option 2 — context

The sprint prompt offers two design choices and asks Pass 1 to pick one. Critical context the prompt lacked: **`walkforward_windows` table does not exist** in `src/schema/registry.py` (verified via grep). Window-level metadata lives only in-memory in `WalkForwardRunResult.window_metrics`, `window_power`, `window_states` — and is reduced to scalar counters (`n_windows_pass`, `n_windows_fail`, `n_windows_inconclusive_data`, `n_windows_inconclusive_power`) on the `walkforward_results` row.

This shifts the cost calculus:

| | Option 1 (new sub-state) | Option 2 (column on `walkforward_windows`) |
|---|---|---|
| Schema change | +1 column on `walkforward_results` (`n_windows_inconclusive_duration INTEGER`) | **+1 NEW table** `walkforward_windows` (run_id, window_index, train_start, train_end, test_start, test_end, window_duration_days, state) |
| State machine | +1 sub-state constant `WINDOW_INCONCLUSIVE_DURATION`, prepend duration check in reducer | none (operator interprets) |
| Runner work | flag short windows in `count_power_states`, increment new counter | persist all window rows + duration |
| Postgres sync | +1 column (incremental) | new table sync_mode, new sync_pk |
| Operator signal | direct: outcome row tells you "INCONCLUSIVE because window too short" | indirect: operator reads window table + applies threshold mentally |
| Promotion gate impact | `check_promotion_gate` already reads the run-level row — sub-state automatically respected | gate must learn to read second table |
| Dashboard impact | one new chip color for the new sub-state on existing window matrix | new table needs new component |

### Decision B1 — Option 1 (new sub-state INCONCLUSIVE_WINDOW_DURATION)

**Chosen.** Reasons:

1. **Direct signal.** The whole point of the sprint is "operator can distinguish short-window INCONCLUSIVE from under-signal INCONCLUSIVE." Option 1 puts that distinction *inside the outcome reducer*, so it surfaces in every consumer (validation docs, dashboard, promotion gate, JSON outputs) for free. Option 2 surfaces the raw duration but expects every consumer to apply the threshold themselves — that's drift waiting to happen.
2. **No new table.** Option 2 requires creating `walkforward_windows`, designing its sync, and adding indexes. Option 1 adds one INTEGER column. Per the sprint prompt: "no new file over 300 lines" / "no scope-creep" — Option 1 is strictly tighter.
3. **State enum is the right place.** The framework already encodes window outcomes as a 4-value enum (`PASS / FAIL / INCONCLUSIVE_POWER / INCONCLUSIVE_DATA`). Adding a 5th value (`INCONCLUSIVE_DURATION`) is a clean extension — the existing reducer pattern handles it without restructuring.
4. **Stronger framework signal** (the sprint prompt's own framing): operator reading any v0.25.4+ validation doc sees `n_windows_inconclusive_duration: 1` instead of having to compute window lengths in their head.
5. **Simpler retrofit.** v0.25.3 Window 4 (274 days) gets re-classified automatically when the new code runs against the same trade fixture. Option 2 would persist the duration but leave the v0.25.3 outcome state unchanged — defeats the retrofit purpose.

### Decision B2 — Threshold: 365 days

**Chosen.** Rationale:

- DEFAULT_WINDOWS in `src/platform/rigor/walkforward_config.py:78-84` are four 15-month windows (~456 days) plus one 9-month window (274 days, the v0.25.3 outlier).
- 365 = 1 calendar year. Falls cleanly between the standard 15-month design (456) and the 9-month outlier (274).
- 1 year of OOS test data is the minimum needed to cover ~1 cycle of seasonal effects (earnings cycles, year-end window-dressing, etc.). Less than 1 year structurally cannot deliver tier-2 regime coverage.
- Threshold lives in `walkforward_config.py` as `MIN_WINDOW_DURATION_DAYS = 365`, paralleling the existing `MIN_TRADES_PER_WINDOW = 10` constant. Override-able per-config for tests.

The threshold is conservative — it flags Window 4 (274d) as too short, leaves the four 15-month windows alone. Pass 2 will additionally verify that no other windows in current or proposed config files fall in the 274-365 day "questionable but not flagged" zone.

### Decision B3 — Precedence: INCONCLUSIVE_DURATION beats INCONCLUSIVE_DATA

**Chosen** (per the sprint prompt: "Takes precedence over INCONCLUSIVE_DATA for that window").

A window that is too short almost certainly won't have enough trades. Without precedence, the duration signal would be invisible (always shadowed by INCONCLUSIVE_DATA). Per-window logic in `count_power_states`:

```
if window_duration_days < MIN_WINDOW_DURATION_DAYS:
    state = WINDOW_INCONCLUSIVE_DURATION
elif n_trades < min_trades_per_window:
    state = WINDOW_INCONCLUSIVE_DATA
elif power.is_underpowered:
    state = WINDOW_INCONCLUSIVE_POWER
elif power.is_pass:
    state = WINDOW_PASS
else:
    state = WINDOW_FAIL
```

In the run-level reducer (`reduce_outcome`), the new check goes before INCONCLUSIVE_DATA:

```
if n_incduration >= inconclusive_window_threshold:
    return INCONCLUSIVE("duration_inconclusive")
if n_incdata >= inconclusive_window_threshold:
    return INCONCLUSIVE("coverage_inconclusive")
... (rest unchanged)
```

`inconclusive_window_threshold` defaults to 2 — so a single short window doesn't flip the run to overall INCONCLUSIVE_DURATION; two would. Matches existing semantics for INCONCLUSIVE_DATA. Pass 2 will sanity-check this against the v0.25.3 fixture (1 short window, 4 standard → run-level should remain INCONCLUSIVE_DATA from the existing path, but Window 4 itself flips state to INCONCLUSIVE_DURATION).

### Anti-goals (Part B)

- **No changes to window generation logic.** DEFAULT_WINDOWS stays at the same 5 windows. Operators who want different windows pass them via `WalkForwardConfig(windows=...)` — that path stays open.
- **No framework-wide aggregation changes** beyond the new counter column.
- **No retro-classification of past `walkforward_results` rows.** The new sub-state surfaces on future runs; existing rows keep `n_windows_inconclusive_duration = 0` (the default).

## Risks called out

1. **VIX cache hot-path overhead.** Adding one ^VIX lookup per `_build_trade` call. For a 5-window × 100-ticker run that's 500 cache hits — first run materializes 500 small parquet files. Mitigation: per-(start,end) cache means once per window per ticker, repeated runs ~free. Could optimize to one VIX bar pull per window if it becomes a problem; not in scope this sprint.
2. **Window-state precedence cascade.** If we get the precedence wrong, INCONCLUSIVE_DATA could shadow INCONCLUSIVE_DURATION (current behavior) — explicitly tested via `test_inconclusive_duration_takes_precedence_over_inconclusive_data`.
3. **Promotion gate.** `check_promotion_gate` reads `walkforward_results.outcome_state`. New `INCONCLUSIVE` rows with `reason = "duration_inconclusive"` are still INCONCLUSIVE — the gate's three-state logic doesn't need to change. Pass 2 will grep to confirm no consumer hardcodes `reason = "coverage_inconclusive"`.
